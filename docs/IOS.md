# The iOS port

DSH Mobile is an Android app today, and this document is the plan for an iOS sibling that
shares as much of it as possible. It records what exists, what the milestones are, and the
constraints that no amount of code removes — so the decisions do not have to be re-derived.

## Where this stands

The port has started at the bottom, where the sharing is real:

- `core` is a Kotlin Multiplatform module. Everything that never needed the JVM — the wire
  DTOs, the JSON-RPC envelope codec, session folding and classification, the assistant
  stream expansion, the notification classifier, the Markdown sanitizer — lives in
  `commonMain` and compiles for Android, iOS device and iOS simulator. CI compiles all three
  iOS targets on every push **on a macOS runner**, which is what stops shared code from quietly
  growing a `java.*` import again (see "The iOS compile gate" below for why that was not true
  before M2b).
- The JVM-only pieces — the OkHttp transport, the commonmark renderer, the TLS pairing and
  URL plumbing — stayed in `jvmMain`, in the same packages, with the same class names. The
  Android app consumes them exactly as before; nothing about the shipping app changed.
- **M2a moved the transport seam into `commonMain`.** `RpcTransport`, `RpcTransportException`,
  the `MuxSocket`/`WsChannelSink` socket contract, `RemoteStreamMux`, `ConnectionLoop` and
  `TransportFailure` are common now; `OkHttpRpcTransport` and `WsChannel` are the JVM
  implementations behind them. Three platform differences were replaced rather than ported:
  `java.io.InputStream` became kotlinx-io's `Source` (and `java.io.IOException` its
  `IOException`, a typealias of the same class on the JVM, so the app's `catch` blocks are
  unchanged); `java.util.concurrent` atomics and `ConcurrentHashMap` became `kotlinx.atomicfu`
  plus a small copy-on-write `AtomicRegistry`; and the part of failure classification that
  inspects `java.net`/`javax.net.ssl` exceptions became an `expect`/`actual` pair.
- **M2b added the second implementation of that seam, on Ktor.** `KtorRpcTransport` and
  `KtorMuxSocket` are `commonMain` classes over an injected Ktor `HttpClient`. On iOS that client
  is `darwinHttpClient()` (the Darwin engine: `NSURLSession` and `NSURLSessionWebSocketTask`); on
  the JVM the same classes run on Ktor's CIO engine, which is how they are proven before an iOS
  device exists: the transport contract tests run against OkHttp *and* Ktor, and the conformance
  suite runs against the pinned real harness once per transport (`-Pdsh.transport=ktor`). The
  Android app is unchanged: it keeps `OkHttpRpcTransport`/`WsChannel`, and its build excludes
  Ktor from the APK (about 2 MB of jars it would otherwise carry for nothing).
  `TransportFailure.ios.kt` classifies what the Darwin engine really throws, by `NSURLErrorDomain`
  code, and relay certificate pinning is implemented on the Darwin challenge handler (see
  "Relay pinning on iOS").
- **M2c moved the rest of the wire layer into `commonMain`.** `DshApiClient`, `Harness021Api`,
  `ReasoningTranslation`, `RpcMultipart`, `HarnessSession`, `RelayPairing` and `HarnessLaunchLine` are
  common now, so everything the iOS app needs to talk to a harness compiles for iOS. What they used to
  take from OkHttp or the JDK went behind four small seams, each with the Android implementation
  unchanged and an iOS one held equal to it by a test that runs both (see "The connect flow on iOS").
  The Android app still reaches no Ktor class, and a test now fails the build if it could.
- **M3a is the first iOS app, and CI runs it.** `:iosShared` (renamed `:sharedUi` in M4a) is a Compose Multiplatform module that
  builds the static framework `DshShared`; `iosApp/` is a SwiftUI shell around it, with its Xcode
  project generated by XcodeGen. The app is one real screen (an address, Connect, and the honest
  result of a probe plus the mux handshake over the Darwin engine). The `ios-app` job runs
  `HarnessContractTest` on an iOS simulator (the first execution of `NSURLSession` under the transport),
  builds the app, installs and drives it in a simulator and screenshots seven scenarios; the `ios-ipa` job
  produces an **unsigned device `.ipa`** as a workflow artifact. The first run found two real differences
  between the Darwin and JVM transports (a mux upgrade refused with 401 never reports, and messages over 1 MiB
  fail the stream). See also "The iOS app", "ATS and the local network" and "Installing on an iPhone".
  Nothing is released from it yet.
- **M3b-1 replaced the iOS mux socket.** Both of those differences were in Ktor's WebSocket wrapper on the
  Darwin engine, not in `NSURLSession`. `DarwinMuxSocket` (in `iosMain`) is a `MuxSocket` written directly on
  `NSURLSessionWebSocketTask`: it sets `maximumMessageSize` to 128 MiB before `resume()`, reads the HTTP status of
  a refused upgrade off the task's response, and reports a host-initiated close as a clean one. The app layer
  asks for it through `platformMuxSocketFactory` (common; the JVM actual is the `WsChannel` on OkHttp that
  Android has always run, and the Android app does not call it). `KtorMuxSocket` stays as the JVM-tested
  multiplatform reference. The contract tests that M3a pinned as Darwin exceptions are unconditional now, and
  run on the simulator against the real socket. See "The Darwin mux socket".
- **M4a made the UI shared, and moved the first screen.** `:sharedUi` is a library for Android and iOS now: the
  Android app consumes it, the iOS framework is built from it. The design system (theme, type, shapes, the
  components) and the **Connect screen** are common Compose code that both apps run, with its decisions in a plain
  `ConnectController` that the Android view model owns and the iOS entry point drives. The Android Connect
  screen is pixel-identical to what it was (see "The shared UI"), and the iOS one is no longer a stand-in: it is
  that screen, over the Darwin client, with what iOS cannot offer yet hidden. See "The shared UI".
- **M4b moved the Pair screen and turned on relay mode.** The Pair screen (the QR scan, the typed address and passcode,
  every failure) is `PairContent` in `:sharedUi` now, with its decisions in a plain `PairController` that the Android
  view model owns and the iOS entry point drives. The Android Pair screen is pixel-identical to what it was (see "How M4b
  was verified on Android"). On iOS, Relay mode is no longer hidden: a relay is paired through the same screen, its
  bearer token is kept in the Keychain, its key is pinned on the unary calls and on the mux socket, and the QR scanner is
  AVFoundation. A simulator has no camera, so CI pairs through the typed form and through a launch argument that hands the
  controller what a scan would have decoded, against pairing relays in the mock harness, one of which speaks TLS with a
  self-signed key. See "Pairing on iOS".

## The iOS compile gate

Kotlin/Native builds Apple targets on macOS only. On Linux and Windows Gradle logs that
`iosArm64, iosSimulatorArm64, iosX64` "cannot be built on this machine and are disabled" and marks
every iOS task `SKIPPED`, so the `./gradlew :core:compileKotlinIosArm64 …` step that M1 added to the
ubuntu `build` job reported `BUILD SUCCESSFUL in 1s` having compiled nothing. Klib cross-compilation
does not rescue it: with `kotlin.native.enableKlibsCrossCompilation=true` on Linux the toolchain
fails to find even `org.jetbrains.kotlin.native.platform.posix`, because it ships no Apple platform
libraries.

So the first real iOS compile was M2b's, and it found three pieces of `commonMain` that were
JVM-only all along (`toByteArray(Charsets.UTF_8)`, `RegexOption.DOT_MATCHES_ALL`, and `Dispatchers.IO`
used from common code), all fixed. The compile now lives in its own `ios-compile` job on
`macos-latest` (free for a public repository), and asserts that the three `core.klib` files exist so
a skip can never pass again. On a host that cannot run it, `./gradlew :core:compileCommonMainKotlinMetadata`
resolves `commonMain` against common declarations only and catches the same class of mistake locally;
it is a smoke check, not the gate.

## Transport parity: Ktor against OkHttp

Both implementations sit behind `RpcTransport`/`MuxSocket` and are held to one contract by
`TransportContractTest`, `TransportSeamTest`, `ProxyTransportTest` and `MuxSocketContractTest`
(each runs once per implementation), and by the real-harness conformance suite. What matches:
the hand-spelled `Host` (default port omitted, IPv6 bracketed), `Content-Type: application/json;
charset=utf-8`, `Authorization`/`Cookie` only when given, the reverse-proxy prefix and its escape
refusal (`HarnessEndpoint` is checked against `resolveHarnessUrl` over 12 bases × 25 routes),
30 s default connect/read deadlines, no read deadline for `pluginManager/installBundle` and
`waitForInstall`, ten minutes for downloads and uploads, the full non-2xx → `RpcTransportException`
table (401/403 apart, the relay's 403 reason, `Retry-After` on 429, 413, 502), multipart answers as
raw bytes, a live `Source` for downloads that is closed when the consumer returns, a consumer's own
exception passing through unwrapped, uploads that stream and report every 64 KiB plus the total, and
the mux socket's credentials, `Host`, rejected-upgrade shape, queueing before the handshake,
idempotent `start`/`close`, and ping answering.

What does not match, and why:

- **Redirects are not followed** by the Ktor transport (OkHttp's default client follows them). An
  `/api` call that is redirected becomes a non-2xx `RpcTransportException`, so a credential is never
  replayed at another address. Darwin refuses redirects itself.
- **A body that ends short of its `Content-Length` fails the call.** Ktor's CIO engine ends such a
  body quietly (OkHttp throws), and a half-saved session ZIP must not look whole. The check is off
  for the Darwin client, where `NSURLSession` reports a short body itself and may decompress while
  leaving the compressed length in the headers (`DshBodyLengthCheck`).
- **No write timeout, and on iOS no separate connect timeout.** OkHttp has `writeTimeoutMs`; the
  Ktor transport has one idle (`socketTimeout`) deadline, and `NSURLRequest.timeoutInterval` is a
  single idle timeout that also covers connecting, so on Darwin the connect deadline folds into the
  read one.
- **Compression.** OkHttp negotiates gzip; Ktor on CIO does not (tests only). `NSURLSession` does.
- **IDN hostnames** must be given as punycode; OkHttp converts them, `HarnessEndpoint` refuses
  non-ASCII hosts.
- **Frame limit.** On the JVM the Ktor mux accepts messages up to 128 MiB (OkHttp has none), and so does
  `DarwinMuxSocket`, which sets the task's `maximumMessageSize` before `resume()`. A mux through **Ktor's**
  WebSocket on the Darwin engine does not: the `WebSockets` plugin sets the limit after the upgrade has
  completed, `NSURLSession` keeps the 1 MiB it started with, and a 3 MiB text frame fails the stream with
  `NSPOSIXErrorDomain 40 "Message too long"` (found by the first simulator run). That is why the iOS app does
  not use it; a long session's `session/follow` opening snapshot can exceed 1 MiB.
- **Download memory on iOS.** `NSURLSession` pushes data as it arrives and Ktor's Darwin engine
  queues it in an unbounded channel, so a consumer slower than the network does not slow the download
  and the unread part is held in memory. The `Source` the consumer reads is live and nothing is
  copied a second time, but the "bytes are pulled from the connection as `consume` reads them"
  guarantee of the OkHttp path is not available on Darwin. A session export is a file written to
  disk, which is normally faster than the link.
- **A rejected mux upgrade through Ktor's Darwin WebSocket loses its status** (the iOS app does not use it).
  Observed on the simulator in M3a: a `403` arrived as `NSURLErrorBadServerResponse` and classified as "not a
  harness", and a `401` was never reported at all: nothing reached the sink even after 20 s. `DarwinMuxSocket`
  reports a refused upgrade as an `RpcTransportException` with the real status, so 401 and 403 are apart on
  iOS as they are on the JVM; see "The Darwin mux socket" for how it finds the status.
- **`WsChannel` never reports a host-initiated clean close** (it has no `onClosing` handler, so OkHttp
  never reaches `onClosed` until something fails). `KtorMuxSocket` reports it. Android's behaviour
  is deliberately untouched; it is worth a look separately.
- **After a local `close()`**, `WsChannel` reports a "Canceled" failure to the sink and `KtorMuxSocket`
  reports nothing; the mux already knows.
- Ktor adds `Accept`, `Accept-Charset` and a `User-Agent`; OkHttp adds `Accept-Encoding` and its own
  `User-Agent`. Neither side reads them.

Until M3a none of this had run on Darwin; `HarnessContractTest` now runs the same 40 cases on the JVM and on
an iOS simulator, against the same fixture harnesses, and "The Darwin engine on a simulator" below says what
it found. Still not exercised: a physical device, and TLS against a certificate a CA signs. (The WebSocket ping/pong
used to be on this list; the mux socket's keep-alive case now proves the simulator answers a host's pings. TLS, the
pinned handler and the trust-on-first-use handler came off it with M4b: see "Relay pinning on iOS".)

## The Darwin engine on a simulator

`HarnessContractTest` (40 cases in `commonTest`; 33 when M3a wrote it) runs on the JVM over Ktor's CIO engine against in-process
fixture harnesses, and on an iOS simulator over `darwinHttpClient()` against the same fixtures as a separate
process (`mock-harness --ci-fixtures`, see `CiFixtures`). First run: iOS 26.5 simulator on an iPhone 17 Pro,
Xcode 26.6, Kotlin/Native 2.0.21, Ktor 3.0.3. **30 of the 32 cases first written held on Darwin as written, with
no change to the transport. The two that did not are real differences, now pinned as known ones (the JVM still
proves the contract), and a 33rd case records the silent 401 with its timing.**

*Behaviours that match the JVM, and so are no longer guesses:*

- **`Host`** reaches the wire exactly as the transport spells it (`127.0.0.1:3181`), in the unary transport
  and in the plain carrier, although `NSURLSession` documents `Host` among the headers it manages.
- **`Authorization` and `Cookie`** are on the wire only when given, byte for byte, on unary calls and on the
  mux upgrade; there is no cookie storage to add one (the session's `Cookie` is the only one the server sees).
- **Bodies**: a UTF-8 body (including a 4-byte character) arrives with `Content-Type: application/json;
  charset=utf-8` and a `Content-Length` equal to its byte length; 12 parallel calls do not cross their answers.
- **The status table** (401, 403, 404, 413, 429 with `Retry-After`, 500, 502) maps to the same
  `RpcTransportException` and the same `TransportFailure` as on the JVM.
- **Redirects** are not followed: a 302 on a unary call is a 302 exception, and the plain carrier hands back the 302
  with its `Location`. A 303 from the harness's index route arrives with `Set-Cookie` readable, so the launch-token
  exchange works (`HarnessSession.exchange` returns the cookie, and refuses a wrong token with 401).
- **Repeated `Set-Cookie`** headers are all readable, folded or not (the test accepts either form; which one
  Darwin produces was not recorded).
- **Streams**: a 300 KiB download comes back byte for byte with its `Content-Type` and `Content-Disposition`; a
  consumer's own exception passes through unwrapped; a 200 KiB upload reaches the harness byte for byte (its
  digest matches) with a non-decreasing progress ending at the total; a multipart answer is the raw bytes.
- **Failures**: a closed port is `REFUSED` (`NSURLErrorCannotConnectToHost`, underlying POSIX 61), a name that
  does not resolve is `DNS`, a server that never answers is `TIMEOUT` at the read deadline (1.5 s here), and a
  cancelled call returns promptly and leaves the client usable.
- **The mux** reaches `ready` (the host's home and the client id arrive intact), carries the session cookie and
  the relay's bearer token on the upgrade, and fails as `REFUSED` against a closed port. A 403 upgrade
  classifies as "not a harness", as documented.

*Where Darwin differed, both through Ktor's WebSocket and both fixed by `DarwinMuxSocket` (see "The Darwin mux
socket"):*

1. **A mux upgrade refused with 401 never reported** (see "Transport parity"). On the JVM the sink hears the 401 in
   about 30 ms.
2. **The mux received at most 1 MiB per message** (see "Frame limit" above).

*Other observations:*

- `NSURLError` descriptions are **localised by the device language** ("Connexion au serveur impossible." on a
  French device). Nothing classifies on that text (`TransportFailure.ios.kt` reads the error domain and code),
  but the `detail` shown beside a failure is the OS's own words, in the user's language, unlike the JVM's.
- A WebSocket task ignores the request's connect timeout; a mux attempt is bounded only by the loop's 3 s open
  deadline.

*The way out of the two differences* was one piece of work, done in M3b-1: a Darwin `MuxSocket` written directly
on `NSURLSessionWebSocketTask` (next section). The contract tests above are what it is held to: the three rig
flags that pinned the exceptions (`muxFenceVerdict`, `muxUnauthorizedIsReported`, `muxAcceptsLargeMessages`) are
gone, because every mux assertion holds on both platforms.

## The Darwin mux socket

`DarwinMuxSocket` (`core/src/iosMain`) is what the iOS app's mux rides on. `platformMuxSocketFactory(url,
authorization, cookie, connectTimeoutMs, pinnedSpkiSha256, observedKey)` (common) returns the `MuxSocketFactory`
the connection loop wants: `DarwinMuxSocket` on iOS, `WsChannel` over OkHttp on the JVM (the Android app builds
its own sockets from its shared client and does not call it). `KtorMuxSocket` was kept: it is the multiplatform
reference that the JVM contract test and the real-harness conformance suite (`-Pdsh.transport=ktor`) run, which
no longer says anything about iOS but still says that the contract is implementable on a second library, and
removing it would leave `WsChannel` the only socket the JVM tests hold to the shared assertions.

**Design.**

- One `NSURLSession` per socket, created in `start()`, on a serial `NSOperationQueue`, with a delegate that only
  forwards to the socket. Every sink callback runs on that queue, one at a time and in order, never on the
  caller's thread (the `RemoteStreamMux` contract), and nothing holds a lock while calling out. `send` and
  `close` touch atomics only.
- The request carries `Authorization`, `Cookie` and a hand-spelled `Host` (the target is the one `KtorMuxSocket`
  builds, `muxTargetOf`, so a reverse-proxy prefix, IPv6 and default ports agree); redirects are refused and the
  session has no cookie storage, as for the unary client.
- `maximumMessageSize` is 128 MiB and is set before `resume()`. The session's idle and total timeouts are
  widened, and the request's too, so nothing but the handshake clock can end an idle mux.
- A receive loop re-arms after each text message. The host's Close frame ends it with an error, in either order
  with `didCloseWithCode`, so the socket decides at the end of the loop (after what was already buffered is
  delivered) and uses `didCloseWithCode` / `task.closeCode` only to say *clean or failure*. `onClosed(null)` for a
  close, `onClosed(cause)` otherwise.
- A rejected upgrade is `RpcTransportException(status, carrierMessage(status))`, with the status read from
  `task.response` (and from a challenge's `failureResponse` or a refused redirect, if either arrives before the
  task's own completion), so 401 and 403 stay apart. A failure with no response is a `DarwinSocketException` whose verdict comes from
  `classifyNSError`, so refused, DNS, timeout and TLS read the same as through the unary client.
- `connectTimeoutMs` is the socket's own clock, because `NSURLSession` ignores the request timeout for a WebSocket
  task; it only fires for a handshake that never finishes. A refusal does not wait for it: `didCompleteWithError`
  arrives at once (about 10 ms against the fixtures) with the status on `task.response`.
- **No leak.** `NSURLSession` retains its delegate until it is invalidated and the delegate reaches the socket,
  which reaches the session. `finish` (every failure and clean close), `close()` and the deadline all call
  `invalidateAndCancel()`, and a socket that is never started never creates a session. After a local `close()` the
  socket reports nothing, like `KtorMuxSocket`; `WsChannel` reports a "Canceled" failure.

**Pinning and trust on first use** are the unary client's own handlers, `pinnedChallengeHandler` and
`learningChallengeHandler`, called from the session delegate's `didReceiveChallenge` for server-trust challenges
only, so a pinned relay's mux is pinned exactly like its unary calls: the leaf key must match, there is no fallback
to system validation, anything unreadable cancels the challenge. A refused key surfaces as the same
`IosPinMismatchException` (`hasPinMismatch`, `CERTIFICATE_PIN`): the socket keeps its own `PinMismatchLog` and
checks it when the task ends with `NSURLErrorCancelled`. A pinned socket must be `wss://`
(`platformMuxSocketFactory` refuses a pin on a plaintext address, because a pin cannot be enforced on a connection
with no TLS and connecting in the clear would turn a typo into a downgrade), a pin and an `ObservedKey` cannot
be combined, and a blank pin is refused, all where the factory is called. Any other challenge (HTTP
authentication, a proxy) is cancelled: the socket has no credential to give, and its identity is in the headers.
**Exercised since M4b:** the mock harness has a pairing relay that speaks TLS with a self-signed key, and the simulator
pairs with it, so the pinned handler has run on the socket: a relay paired by a scanned QR is reconnected to over `wss://`
pinned to its stored key, in a new launch, from the Keychain's token (see "Relay pinning on iOS"). **Not exercised:** a pinned
socket whose stored key no longer matches the relay's (the unary client's mismatch is exercised; the socket's would report the
same `CERTIFICATE_PIN` by the same `PinMismatchLog` path, but no scenario drives it), and the learning handler on the socket,
which the app never asks for (it only learns a key on the unary pairing call).

**Ping.** `NSURLSessionWebSocketTask` answers a host's RFC 6455 ping with a pong on its own, and the socket
therefore has no heartbeat code. This is established by behaviour, not by a citation, because there is nothing
authoritative to cite: Apple's documentation describes only the client's own ping (`sendPing(pongReceiveHandler:)`,
<https://developer.apple.com/documentation/foundation/urlsessionwebsockettask/sendping(pongreceivehandler:)>) and
says nothing about answering the server's, and a server's ping is not delivered to the app, so the app cannot answer
it. `HarnessContractTest` (`anIdleSocketAnswersTheHostsPings…`) connects to a server that pings every 100 ms and
disconnects a client that has not answered within 500 ms, and requires the message that server sends after 1.5 s,
which a client that did not pong would not live to hear. **Result on the iOS 26.5 simulator: the message arrived**,
after more than a dozen pings (`MUX_PING` in the run's log). The same test passes on the JVM over Ktor's CIO engine,
where the library answers. Verified on one OS version and a simulator only; a device and older iOS releases are not.

**What the simulator measured** (iOS 26.5, Xcode 26.6; `HarnessContractTest`, 40 of 40, run
[42449210553](https://github.com/sorsama/deepseek-harness-mobile/actions/runs/42449210553), the `MUX_` lines and the
socket's own `MUX_TRACE` events are in that job's log). Each outcome and the `NSURLSession` event that decided it:

| Case | Result | Decided by |
|---|---|---|
| Upgrade refused with 401 (browser session posture) | `RpcTransportException(401)`, `UNAUTHENTICATED`, **4 to 9 ms** (the M3a run saw nothing in 12 s) | `didCompleteWithError(-1011)`, `task.response` = 401 |
| Upgrade refused with 403 (the relay without its token) | `RpcTransportException(403)`, `TRUST_FENCE`, apart from the 401 | the same, `task.response` = 403 |
| 401 that carries `WWW-Authenticate` | `RpcTransportException(401)`, 21 ms | an HTTP-auth challenge: `didReceiveChallenge` says 401 in `failureResponse`, the socket cancels it, and **`task.response` is `null` afterwards** (`didCompleteWithError(-999)`), so the status exists only because the challenge's was recorded first |
| Upgrade answered with a 302 | `RpcTransportException(302)`, not followed | `willPerformHTTPRedirection` refused, then `didCompleteWithError(-1011)` with the 302 |
| A 3 MiB text message (3,145,728 characters) | arrives intact, after two smaller messages on the same stream (the M3a run failed it with POSIX 40) | `maximumMessageSize` set before `resume()` |
| Host sends a message and a Close frame (code 1000) | open, the message, **one** `onClosed(null)`, nothing after, `send` false | see below |
| Link dropped after the handshake, no Close frame | `onClosed(DarwinSocketException)`, not a clean close | `receive` and `didCompleteWithError` both end with `NSPOSIXErrorDomain 57` |
| Port with no listener | `REFUSED` (`NSURLErrorCannotConnectToHost`, POSIX 61 underneath) | `didCompleteWithError`, `task.response` = null |
| Host pings every 100 ms, drops a client that does not pong | the 1.5 s message arrives | the system answers the pings |

Two things in the trace are why the socket is built the way it is. First, **a clean close reaches the receive loop
before it reaches the delegate**: the receive completion fails with `NSPOSIXErrorDomain 57 "Socket is not
connected"` first (with `closeSeen=false`), and `didCloseWithCode` (1000) follows a moment later. Deciding at the
receive error would have reported every polite close as a failure, and the *same* error 57 is what a dead link
produces, so only the Close frame (`didCloseWithCode`, or `task.closeCode`) tells the two apart; the socket waits
for it, with a 300 ms fallback if neither the close nor the task's completion ever arrives. Second, the 401 defect
was **in Ktor's WebSocket wrapper and not in `NSURLSession`**: a raw task reports a refused upgrade promptly and
with its status, so the socket does not poll `task.response` while the handshake is pending (a first version did, in
case a refusal produced no callback; the trace showed it never decided anything). The one place the response is
*not* there is the challenge case in the table, which is why the status is also taken from the challenge and from a
refused redirect.

## Relay pinning on iOS

The relay's default posture is a self-signed certificate, so the app pins its key: the pairing QR
carries `base64(sha256(DER SubjectPublicKeyInfo))` and the key *is* the trust decision. On the JVM
that is `RelayTls.pinnedClient`. On iOS it is `darwinHttpClient(pinnedSpkiSha256 = …)`, whose
challenge handler applies the same rules: the leaf certificate's key must match exactly; there is no
fallback to system validation; the hostname is not checked; and every unreadable or absent input
cancels the challenge (it fails closed). A refused challenge surfaces from `NSURLSession` as a bare
`NSURLErrorCancelled`, so the handler records the mismatch first and the client rethrows the failure as
`IosPinMismatchException`, which `hasPinMismatch` finds and which classifies as `CERTIFICATE_PIN`
rather than a generic TLS error.

The pin value must be the number the JVM computes. Apple's Security framework only hands back raw key
bytes, and rebuilding the SubjectPublicKeyInfo header from a table of key types and sizes is how a pin
silently stops matching, so `SpkiPin` reads the SubjectPublicKeyInfo out of the certificate's DER for
any key type, and `SpkiPinTest` holds it equal to `RelayTls.spkiPin` over RSA and EC certificates.
Trust-on-first-use pairing (`RelayTls.trustOnFirstUseClient`) is `darwinHttpClient(observedKey = …)` on
iOS: it accepts the key the relay presents and records it in an `ObservedKey`, fails closed on a
certificate it cannot read, and cannot be combined with a pin. It is the same compromise as on the JVM
(whoever answers during passcode pairing ends up holding the enrolment), and the UI says so (the Pair screen shows
which of the three situations a pairing is in before it is made). Nothing on iOS connects to a relay without either a pin or
an explicit absence of one. The mux WebSocket is pinned the same way: `DarwinMuxSocket` runs these two handlers
from its own session delegate (see "The Darwin mux socket"), so a pinned relay's mux is pinned exactly like its
unary calls and reports the same `CERTIFICATE_PIN` on a mismatch.

**What the simulator has shown (M4b).** The pairing scenarios in `simulator-check.sh` run both handlers against the fixtures'
TLS relay (a fresh self-signed EC key each run, `localhost` and `127.0.0.1` in its names, none of which the handlers look at):

| Scenario | Handler | Result on the iOS 26.5 simulator |
|---|---|---|
| a scanned QR carrying the relay's key | pinned, on the unary claim | paired; the stored record has `useTls` and the key |
| the connection that follows | pinned, on `DarwinMuxSocket` (`wss://`) | connected, with the bearer token |
| a new launch, nothing passed | pinned, on the mux, key and token read back from `NSUserDefaults` and the Keychain | connected |
| a scanned QR carrying a different key | pinned, on the unary claim | refused as `CERTIFICATE_PIN`; nothing stored |
| a typed `https` address | learning, on the unary claim | paired; the relay repeated its key and that is what is pinned afterwards |

What is **still unverified**: a physical device, and the system-trust path against a certificate a CA signs (every fixture is
self-signed, so the "neither a pin nor a learning client" case is only run against plaintext). Neither handler checks the host
name by design, so a relay reached by another name than its certificate's is not a case. A relay that rotates its key under a
paired phone is not driven either.

## The connect flow on iOS

`HarnessSession` (the launch-token exchange) and `RelayPairing` (health, origin discovery, claim) were
the last pieces of the connect flow tied to OkHttp. They are common code over two small seams, and
`DshApiClient` and `RpcMultipart` over two more. In each the JVM actual is what the Android app has
always run, so none of it changed on Android; the iOS side is held to it by a test that runs both.

- **`PlainHttp`** (`PlainHttp.kt`): one GET or POST with headers, an optional UTF-8 body and per-request
  deadlines. It never follows a redirect (the exchange reads its cookie off a 303 and discovery reads a
  `Location`), returns any status as an answer, and fails with an `IOException` that
  `TransportFailures.classify` can read. `OkHttpPlainHttp` wraps the app's shared client, and a pinned or
  trust-on-first-use client is just such a client; `KtorPlainHttp` is the multiplatform one, on the
  Darwin client on iOS. `PlainHttpContractTest` runs ten behaviours against both. Two things differ
  from before on Android, both improvements: a body that dies mid-read now fails the call (the relay
  code threw inside OkHttp's callback, which logs it and leaves the caller waiting), and cancelling the
  caller now aborts the launch-token exchange (it ran to its deadline on an IO thread). Darwin folds
  repeated `Set-Cookie` headers into one value joined by `", "`, so the exchange also looks for the
  session cookie after such a join; OkHttp never produces one.
- **`WireUrl`** (`WireUrl.kt`): is this an `http(s)` address, what are its host, port and path, where
  does this `Location` point, what is this route under this base, and the base with `?token=` added.
  On the JVM each is `HttpUrl`, carried through as the same object. On iOS it is `PortableUrls`, and
  `PortableUrlsTest` runs it and OkHttp over about 60 addresses, about 35 refusals, 8 bases by about 45
  references and 15 bases by 15 harness routes. They agree apart from: **internationalised and percent-encoded host
  names are refused** (OkHttp converts them to punycode; type them as punycode, as for
  `HarnessEndpoint`); **unusual IPv6 and IPv4-mapped spellings are kept as typed** rather than
  canonicalised (`[0:0:0:0:0:0:0:1]`, `[::ffff:192.168.1.5]`); and **fragments and user info are left
  out of the text** (`hasCredentials` still says they were there).
- **`readMultipartParts`** (`MultipartParts.kt`): harness 0.1.7's multipart answers. The JVM actual is
  OkHttp's `MultipartReader`; iOS uses `PortableMultipart`. `PortableMultipartTest` compares them over
  tables of media types and bodies, every truncation of a body, 4,000 generated messages with delimiter
  look-alikes in the payload and 6,000 randomly damaged ones. A body OkHttp refuses is refused, though
  not with the same exception type (an I/O error on the JVM, `IllegalArgumentException` here).
- **`encodeQueryComponent` and `decodeBase64`** (`WireText.kt`): the two things `DshApiClient` took from
  `java.net` and `java.util`, written out and held equal to the JDK (and, for the query value, to
  OkHttp's `addQueryParameter`). A lone surrogate is written as `?` on every platform; the JDK is not
  consistent about it and nothing a harness or the OS hands out contains one.

### No Ktor on the Android path

`app/build.gradle.kts` excludes `io.ktor` from the app's dependency on `:core` and release minification
is off, so a `:core` class that reaches a Ktor type compiles, passes every unit test (the app's tests put
Ktor back) and crashes the shipped APK with `NoClassDefFoundError` the first time it loads. The rule is
an island: only `KtorRpcTransport`, `KtorMuxSocket`, `KtorPlainHttp`, `HarnessEndpoint` and
`PortableUrls` (and their helpers in those files) may mention Ktor, and nothing outside the island may
mention them. `NoKtorOnTheAppPathTest` reads the compiled `:core` classes (constant pools, so a type
that appears only in a signature counts) and the sources, and fails naming the offender. The
`expect`/`actual` seams above are how common code reaches the JVM-only implementations without
naming either.

### What stayed in `jvmMain`, and why

- `HarnessUrl.kt` (`resolveHarnessUrl`): returns OkHttp's `HttpUrl`, which `OkHttpRpcTransport` builds its
  requests from and the app calls; common code reaches it through `resolveHarnessWireUrl`.
- `RelayTls.kt`: an `X509TrustManager` and an `SSLContext` on OkHttp; the iOS equivalents are
  `pinnedChallengeHandler` and `learningChallengeHandler`. (`ObservedKey`, its one piece of plain
  logic, moved.)
- `AutomationTiming.kt`: its validation is `java.time`'s (`Instant.parse`, `ZoneId.of`,
  `LocalTime.parse`). `kotlinx-datetime` would be a new dependency and a different set of accepted
  inputs; it needs checking against the old code input by input, and the Automations screen is not
  needed until the UI is.
- `session/BoundedImageRead.kt`: reads an Android `ContentResolver` `InputStream`, and its contract
  (consume at most one byte past the limit) is a property of that stream type. iOS hands over
  already-bounded `Data`.
- `session/PreviewLinks.kt`: sorts a tapped link by `java.net.URI`, whose strict RFC 2396 parse and
  decoded `path` decide what is `Ignored`. A portable version needs the same kind of proof as
  `PortableUrls` over those rules, which belongs with the Markdown preview on iOS.

## The shared UI

Since M4a the Android app and the iOS app draw the same Compose code. The Android app is still the product: a
screen moves into `:sharedUi` only once the Android screen built from the moved code is pixel-identical to the one
it replaced.

### Layout

`:sharedUi` is a Kotlin Multiplatform library with Compose Multiplatform **1.7.1** (see "The iOS app" for why that
version), with `androidTarget()`, `iosArm64()` and `iosSimulatorArm64()`. It was `:iosShared` until M4a gave it the
Android target and a name that is not about iOS; it is a module of its own and not a `composeApp` inside `:app`
so that the iOS framework does not have to build the Android app to get at the shared half.

| Source set | Holds |
|---|---|
| `commonMain` | the design system (`ui/theme`), the components (`ui/components`), the screens that have moved and the state holders behind them (`ui/screens/connect`, `ui/screens/pair`), the models they speak (`connection`), the Termux state types the Connect screen shows (`termux`), and the small interfaces a platform implements |
| `androidMain` | the Android halves of those interfaces, and nothing the app does not also need: the font loader, the back handler, locale-aware counts |
| `iosMain` | the iOS halves, the iOS app's wiring (stores, networking, the connection, the QR scanner) and its entry point |
| `commonTest` | the moved tests, which run on the JVM through the Android unit-test task and on an iOS simulator |

Everything that moved kept its package, so the rest of the Android app compiles against it unchanged. `:app`
depends on `:sharedUi` and excludes Ktor from the edge, exactly as it does for `:core`; `commonMain` and
`androidMain` never name Ktor (`SharedUiHasNoKtorOnTheAndroidPathTest` reads the sources and fails the build if
one does), so the iOS-only networking stays in `iosMain`. `-Pdsh.iosOnly=true` leaves the Android library out of
the build, so a Mac without an Android SDK still builds the iOS app.

### Versions: what Android resolves, before and after

`:app:dependencies` for `debugRuntimeClasspath` and `debugCompileClasspath`, before the change and after it:

| Artifact | Before | After |
|---|---|---|
| `androidx.compose.ui`, `runtime`, `foundation`, `animation` | 1.7.6 | 1.7.6 |
| `androidx.compose.material3` | 1.3.1 | 1.3.1 |
| `androidx.compose.material`, `material-icons-core`, `material-icons-extended` | 1.7.6 | 1.7.6 |
| `androidx.lifecycle` | 2.8.7 | 2.8.7 |

identical before and after. What is new there are `org.jetbrains.compose.*:1.7.1` and
`org.jetbrains.androidx.lifecycle:*:2.8.4` coordinates, and they are redirect POMs: their Android variants depend

Moved: the theme and type scale, the buttons, segmented control, bottom sheet, hold menu, switch, state dot,

### The ports, and what iOS does with each

`ConnectController` asks a platform for five things (`ConnectPorts.kt`):

| Port | Android | iOS |
|---|---|---|
| `ConnectStore`: remembered harnesses and the Connect settings | `HostsStore` through `AndroidConnectStore` (Preferences DataStore, unchanged) | `UserDefaultsConnectStore`: `NSUserDefaults`, the same `HostConfig` JSON |
| `ConnectNetwork`: probe, sweep, relay browse, subnet | `DiscoveryEngine` and `MdnsDiscovery` | the Darwin client: one `session/canOpenWorkspacePath` call, classified; no sweep, no browse |
| `ConnectionLink`: the live connection | `ConnectionManager` | `IosConnectionLink`: `ConnectionLoop` over `DarwinMuxSocket` |
| `HarnessSignIn`: launch token to browser session | `HarnessSessionStore` | `IosHarnessSignIn`: the exchange over `NSURLSession`; the session goes to the **Keychain** |
| `LoopbackHarness`: the harness on this device | `TermuxLoopbackHarness` | none (`NoLoopbackHarness`) |

`PairController` asks for one more (`PairPorts`), because pairing is one exchange and each part of it is the platform's:

| Part | Android | iOS |
|---|---|---|
| `withHttp(fingerprint, observed)`: the client a claim is made over | `OkHttpPlainHttp` over the pinned client (`HarnessClientFactory`), `RelayTls.trustOnFirstUseClient`, or the app's client | `KtorPlainHttp` over `darwinHttpClient(pinnedSpkiSha256 = …)`, `darwinHttpClient(observedKey = …)` or `darwinHttpClient()`, one per call and closed after it |
| `rememberRelay`: the relay's record | `HostsStore.rememberHost(relay = RelayIdentity(…))` | `UserDefaultsConnectStore.rememberRelay` (the same record, in `NSUserDefaults`) |
| `storeToken`: the bearer token the relay shows once | `RelayCredentialStore` (AES-GCM under an `AndroidKeyStore` key) | `KeychainRelayTokens` (the Keychain, `AfterFirstUnlock`, one item holding a map from the relay's id to its token) |
| `connect` | `ConnectionManager` | `IosConnectionLink`, which now sends the bearer, takes no browser cookie for a relay, and pins the mux socket to the relay's key |
| `deviceName` | `Build.MANUFACTURER` and `Build.MODEL` | `UIDevice.name` (the system answers "iPhone" to an app without the user-assigned-name entitlement; the field is editable) |

A `ConnectFeatures` value tells the screen what its platform offers, and a section that could never work is
hidden, never shown broken. On iOS today: **no "This phone"** (iOS does not allow the background processes
Termux relies on, so it cannot exist there, and no amount of code changes that), **no subnet sweep and no relay
discovery** (they need the device's own addresses, mDNS and the Local Network permission decisions, M3b), **no Settings
button**, and none of the auto-connect options that depend on those. What is there is the part that works: a typed
address, the Recent list with live status, "reconnect to the last harness", the connecting takeover, every failure with
its advice, signing in with a launch token, and, since M4b, **Relay mode**: the relays this device has paired with, with
the live status of each, and the Pair screen to add one. (Relays are listed, not discovered: nothing browses for them,
so a relay is found by pairing with it.) After a connection the iOS app shows a plain "Connected" page (which harness,
its home, this client's protocol baseline, Disconnect) until the session list moves.

### Strings

The strings of a moved screen are Compose Multiplatform resources in `sharedUi/src/commonMain/composeResources/values*/strings.xml`,
in all 11 locales, generated from the Android resources with the wording unchanged
(`node tools/shared-strings/sync.mjs`; the only edit is dropping the backslash of Android's `\'`). Two string
systems coexist for now, and the rule that keeps them honest is:

- a string the shared code reads (`Res.string.<key>`) lives in the shared files; a string only the shared code reads
  is removed from the Android resources (`--prune`), so there is one copy;
- a string both the moved and the unmoved code read stays in both places, and `SharedResourcesTest` (in `:app`, so
  it runs wherever the Android tests run) fails if any of the 11 locales differs between them;
- the same test fails if a string the shared code reads is missing from a locale, if a shared string is not read by
  anything, or if one uses a format Compose Multiplatform does not fill in (it fills `%1$s` and `%1$d` and nothing else);
- a number goes through `localizedCount` first and reaches the text as a String.

Known wording problem, carried over unchanged on purpose: `connect_fail_streams` says "Android can also freeze the
app right after launch", which is true of the phone it was written for and odd on an iPhone. Fixing it is a wording
change, which belongs with the translators and in both apps at once.

### The recipe for the next screen

1. Read the screen and everything it uses (`grep` its imports). List what is platform: `android.*`, `java.*`,
   `LocalContext`, `R.*`, Hilt, lifecycle, `Intent`, `Toast`, `String.format`, `SystemClock`, OkHttp.
2. `git mv` the screen's files and the design-system files it needs that have not moved into
   `sharedUi/src/commonMain/kotlin`, **keeping the package**. A file name that exists in both modules is a duplicate
   class (`ConnectScreen.kt` had to become `ConnectContent.kt`), so give the shared file a new name.
3. Put each platform thing behind the smallest interface that names what the screen needs from it (a port for
   state and effects, a `Local…` provided by the host for a capability, an `expect`/`actual` for a function), with
   KDoc that says what each platform does and why they differ.
4. Move the view model's decisions into a plain class over those ports. The Hilt view model keeps the Android
   wiring and owns an instance; the iOS entry point builds its own.
5. Strings: run `node tools/shared-strings/sync.mjs --prune`, then `SharedResourcesTest`.
6. Make `internal` things that the unmoved code uses public (compile errors say which), move the screen's tests
   to `commonTest` (`com.labteto.dshmobile.testing` has the JUnit-order assertions), and build `:app`.
7. Verify on a device: before changing code, build the current `main` debug APK and script the screen's states on
   an emulator (light, dark, 3-button and gesture navigation, a non-English and a right-to-left locale, every
   failure); build the branch and run the same script; compare pixel for pixel with the status bar fixed
   (`adb shell am broadcast -a com.android.systemui.demo`) and animations off. Any difference is a bug or has a
   written reason. A hover highlight caught on one run is the emulator's pointer, not the build: rerun it.
8. Wire the screen into `DshApp` on iOS, add the simulator scenarios that show its states, and read the screenshots.

### How M4b was verified on Android

Emulator DSH_Verify37 (API 37, 1080×2340), animations off, the status bar pinned with the demo-mode broadcast,

## Pairing on iOS

The Pair screen is shared (`PairContent`, `PairController`); this section is what is iOS about it.

**The exchange.** `PairController.claim` tries each origin an invitation names, in order. For each: `RelayPairing.locate`
(over the ordinary Darwin client) resolves a harness's own port to the relay's listener, because a 302 must be read and not
followed; then `RelayPairing.claim` over the client the key situation calls for:

| The address came from | Client | What it enforces |
|---|---|---|
| a scanned QR with a `fingerprint` | `darwinHttpClient(pinnedSpkiSha256 = fingerprint)` | the leaf certificate's key must equal the QR's, before a byte of the claim is sent; no fallback to system validation; a refusal is `CERTIFICATE_PIN` ("The key at … isn't the one this code names. Don't pair.") |
| a typed `https` address | `darwinHttpClient(observedKey = …)` | nothing: it accepts the key it is shown and records it (trust on first use). The relay repeats its key in the claim answer, and that is what is stored |
| a plain `http` address | `darwinHttpClient()` | the notice says so: the token and everything after it travel in the clear |

A QR whose `fingerprint` is blank is not ignored and does not crash the app: it becomes a pin that can match nothing, so
every TLS connection to it is refused as a pin mismatch (a plaintext address has no TLS to refuse, as on Android). A client
is built per call and closed after it, because the three clients are three different `NSURLSession`s.

**Enrolment** keeps the order the Android view model always had: the relay's record (`NSUserDefaults`, the same
`HostConfig` JSON, with the relay's device id, TLS flag, key and token expiry), then the token (Keychain), then the state
that closes the screen, then the connection. The connection is `IosConnectionLink`: for a relay it sends
`Authorization: Bearer …` and no browser cookie (the relay holds the harness session), builds the mux socket with
`pinnedSpkiSha256` when the relay is on TLS, and stops retrying on the failures that retrying cannot fix (a 403 from the relay,
a changed key, the harness refusing the relay's own request), keeping the explanation on screen with "Pair again". Relay cards
in Connect are probed the same way (pinned client, bearer), so they show real status and not a wall of 403.

**The scanner** is `IosQrScanner` (`PairScanner`, the slot `PairContent` takes). It is AVFoundation: an `AVCaptureSession` with
an `AVCaptureMetadataOutput` set to QR, a preview layer in a `UIView` that Compose hosts with `UIKitView`, started off the
main thread. It asks for the camera on arrival, and its notices are Android's, with the same strings: no camera, permission
not given, permission refused (with a button to Settings), the session failing to start, and always "Type the code instead".
`NSCameraUsageDescription` is in the plist and in all 11 `InfoPlist.strings`; AVFoundation is linked by `project.yml`
(a static Kotlin framework does not carry its system frameworks). The sheet is forced dark, as Android's is.

**What iOS does not have yet, on purpose:** no flashlight, no "choose a photo" (a QR in a screenshot needs a `PHPicker` and a
Core Image detector), and no sweeping laser on the frame. They are conveniences on Android; the typed code is the way round
all three, and the scan is the only path that needs a camera. The Pair screen also scrolls a new failure card into view on iOS
(`scrollToFailure`); the Android screen does not and keeps its layout.

**What a simulator can and cannot show.** It has no camera, so the permission prompt, the live preview and the decode are not
exercised anywhere but on a phone, and that stays **unverified** until someone runs it on one. What CI does instead is go down
the same code a scan does: `-DshPairPayload` hands the controller the text a QR would have decoded (an invitation built by the
script), and `-DshPairUrl`, `-DshPairCode` and `-DshPairSubmit` type. Everything after the decode (the claim, the pin, the
Keychain, the connection) is the real thing against the mock harness's pairing relays: port 3186 over plain HTTP, and port 3187
over TLS with a certificate that `keytool` makes when the fixtures start, whose key the fixtures print (`ci pairing:`) for the
script to put in a QR. The code of both relays works every time (a real relay's works once) and `42900000` is always locked out.

## The iOS app

Two pieces:

- **`:sharedUi`** (see "The shared UI") is the Compose Multiplatform module. For iOS it builds one static framework,
  `DshShared`, which holds the screens and the iOS wiring. Compose Multiplatform is **1.7.1**: it is the release built for
  this repo's Kotlin 2.0.21, and 1.7.3 and later are built for Kotlin 2.1 and their klibs do not read on 2.0.21. It
  moves together with `kotlin` (the catalog says so). `iosX64` (the Intel simulator) is left out of the framework:
  every Mac and every macOS runner that matters is Apple Silicon. `:core` still compiles it.
- **`iosApp/`** is a SwiftUI shell: an `@main App` whose one view wraps the Kotlin `MainViewController`.
  There is no checked-in `.xcodeproj`. `project.yml` is the whole project, `iosApp/generate.sh` runs XcodeGen
  on it, and a build phase runs `:sharedUi:embedAndSignAppleFrameworkForXcode` so Xcode links the framework
  for the SDK it is building. The bundle id is `com.labteto.dshmobile`, the name "DSH Mobile", the minimum
  iOS 15.

**The screen** is the Android Connect screen, the same composables (see "The shared UI" for what iOS hides). The
address field takes a bare host, `host:port`, an `http(s)://` URL with a reverse-proxy path or an IPv6 literal, and
the default port is 3080 (the Android app's `parseHostInput`, which is the same code). A connect is the Android app's
own sequence, over the Darwin client:

1. one unary `session/canOpenWorkspacePath` call, which is what `DiscoveryEngine.probe` asks. Every
   harness serves it and its failures arrive classified: refused, timeout, DNS, 403 (the `Host` fence),
   401 (no browser session), not a harness, TLS;
2. the readiness handshake through `ConnectionLoop`: open `/api/remote.mux`, open `$events`, read `ready`.

A harness that answers 401 is remembered, and the connection-lost surface offers **Sign in**: the launch token (or the
whole startup line the harness prints) is exchanged on its index route over `NSURLSession`, the browser session that
comes back is stored in the **Keychain** (one item holding a map from the harness's id to its cookie, as Android's
`HarnessSessionStore` holds one in app storage), and the connection that follows carries it. The Keychain is only
available to a signed app (an unsigned one has no application identifier, and the system answers
`errSecMissingEntitlement`), so the simulator build in CI is signed ad hoc, and the unsigned device `.ipa` gets its
identifier when Sideloadly or AltStore signs it. If a write is ever refused the app keeps the session in memory for the
launch (and prints `DSH_KEYCHAIN add failed, OSStatus=…`): the person loses it at the next launch, not the sign-in they
have just made. Harnesses are
remembered in `NSUserDefaults` and shown in Recent with their live status, and the app reconnects to the last one at
launch unless that switch is off. The result is a "Connected" page with the address, the host's home directory and
this client's protocol baseline. It shows no harness name or version because the wire has none: 0.1.2 removed
`host.describe`, and the ready frame carries only the home directory (the Android details panel shows the same
baseline).

**Strings** are the Android app's own keys and text, in all 11 locales (see "Strings" under "The shared UI"). The
Info.plist permission text is translated in `iosApp/DSHMobile/<language>.lproj/InfoPlist.strings`.

**Version.** `iosApp/scripts/version.sh` reads the one version this repo has, the fallback literal in
`app/build.gradle.kts` (or `DSH_VERSION_NAME`, which the release workflow sets from the tag), and derives the
build number the way `versionCode` is derived. The two apps of a release carry the same numbers.

**Launch arguments (Debug builds only).** They go down the same code paths as a person's taps, so a screenshot shows
what the screen does. CI drives the app with them, and so can a person:
`xcrun simctl launch booted com.labteto.dshmobile -DshConnectAddress 192.168.1.20 -DshAutoConnect YES`.

| Argument | Does |
|---|---|
| `-DshConnectAddress <address>` | pre-fills the address field |
| `-DshAutoConnect YES` | then taps Connect |
| `-DshOpenSignIn YES` | opens the sign-in sheet when the harness wants a session |
| `-DshSignInToken <token>` | opens it and submits the token, as pasting it would |
| `-DshReset YES` | forgets the remembered harnesses, the settings and the Keychain before the screen is built |
| `-DshAutoReconnect NO` | turns off "reconnect to the last harness", which shows the Recent list |
| `-DshReport YES` | writes the result line without a Connect tap |
| `-DshConnectMode relay` | switches the Connect screen to Relay mode (or `lan`) before it is drawn |
| `-DshOpenPair YES` | opens the Pair screen |
| `-DshPairUrl <address>`, `-DshPairCode <digits>` | fill the Pair form (and open it) |
| `-DshPairSubmit YES` | taps Pair |
| `-DshPairPayload <hex of the QR text>` | hands the Pair controller the text a scan would have decoded, so it pairs at once; hex because launch arguments are parsed as property lists, which mangles JSON |
| `-DshPairScanner YES` | opens the camera sheet |

With auto-connect, report or a pairing argument on, the app writes one result line (`DSH_CONNECT_RESULT connected …` or
`… failed kind=…`) to `Documents/dsh-connect-result.txt` in its container, and a pairing run also writes
`DSH_PAIR_RESULT paired authority=… tls=… pinned=…` or `DSH_PAIR_RESULT failed kind=…` to
`Documents/dsh-pair-result.txt` (its own file, so the connection a pairing starts does not overwrite it). A Release
build ignores all of it.

## ATS and the local network

**App Transport Security.** The harness speaks plain HTTP by design, at an address the person types: usually
`http://192.168.x.x:3080`, sometimes a name on their own network or tailnet. ATS blocks plain HTTP to everything
except what its exceptions name, and an exception list cannot be written for an address that is typed at run
time. `NSAppTransportSecurity` therefore sets **`NSAllowsArbitraryLoads = true`**, with
`NSAllowsLocalNetworking = true` beside it. `NSAllowsLocalNetworking` alone covers `.local` names,
unqualified names and local addresses, and would not cover `pc.my-tailnet.ts.net` or `harness.example.org`
over plain HTTP, which are exactly what a person with a harness behind Tailscale types. WebSocket upgrades
(`NSURLSessionWebSocketTask`) fall under the same rule.

*What that means for the App Store, which this build does not go through.* A submission with
`NSAllowsArbitraryLoads` has to justify it in App Store Connect, and an app whose job is to connect to a server
its user names (a Git client, an SSH client, a self-hosted dashboard) is the usual defensible case. The
narrower alternative is to drop `NSAllowsArbitraryLoads`, keep `NSAllowsLocalNetworking`, and tell people
whose harness is not on their local network to put it behind HTTPS (Tailscale serve, a reverse proxy) or the
relay's TLS. Which of the two to submit is a decision for when a submission is made, not for a sideloaded build.

**The local-network prompt.** Since iOS 14 the first connection to a device on the Wi-Fi makes iOS ask whether
the app may find and connect to devices on the local network. `NSLocalNetworkUsageDescription` is the text it
shows, in the 11 languages. Loopback is exempt, so the simulator never shows it and CI cannot exercise it: what a
*denied* permission looks like through `TransportFailure.ios.kt` is unverified until a phone does it.
`NSBonjourServices` is not declared because nothing browses with Bonjour; the harness advertises nothing, and
discovery on Android is a subnet sweep, which is part of the full Connect screen.

## Building and running on a Mac

You need Xcode 16 or newer, a JDK 17 and XcodeGen (`brew install xcodegen`). No Android SDK.

```sh
iosApp/generate.sh                    # writes iosApp/DSHMobile.xcodeproj
open iosApp/DSHMobile.xcodeproj       # pick a simulator or a device, Run
```

The first build downloads the Kotlin/Native toolchain and compiles Compose Multiplatform for the target, which
takes a while; later builds are incremental. Run `generate.sh` again after pulling a change to `project.yml`.
To try the app against the mock harness, build it with `./gradlew :mock-harness:installDist`, start
`mock-harness/build/install/mock-harness/bin/mock-harness --port 3080` (it serves until you press Enter), and
connect to `127.0.0.1:3080` in a simulator, which shares the Mac's network.

The Kotlin tests that run on a simulator need the fixture harnesses up first:

```sh
./gradlew -Pdsh.iosOnly=true :mock-harness:installDist
mock-harness/build/install/mock-harness/bin/mock-harness --ci-fixtures &   # ports 3181, 3182, 3183
./gradlew -Pdsh.iosOnly=true -Pdsh.iosSimulator="iPhone 16" :core:iosSimulatorArm64Test :sharedUi:iosSimulatorArm64Test
```

`-Pdsh.iosSimulator` is the name or UDID of a simulator `xcrun simctl list devices available` shows;
Kotlin/Native's default device name is one a current Xcode no longer ships. `-Pdsh.iosOnly=true` leaves the Android
app out of the Gradle build, which is what lets a Mac without an Android SDK build any of this.

## Installing on an iPhone

The `.ipa` the `ios-ipa` job produces (`DSH-Mobile-<version>-unsigned.ipa`, in the run's
`dsh-mobile-ios-unsigned-ipa` artifact, which GitHub wraps in a zip) is **unsigned**, so it installs on nothing
as it is. There is no Apple Developer account behind it; a sideloading tool re-signs it with the installer's own
free Apple ID:

1. On the iPhone, turn on Developer Mode (Settings, Privacy & Security, Developer Mode; it restarts the phone).
2. Install **Sideloadly** (Windows or macOS) or **AltStore** (AltServer on the computer) and connect the phone.
3. Give it the `.ipa` and your Apple ID. It re-signs the app with a personal team certificate and installs it.
   Sideloadly may append your team id to the bundle id; that is expected.
4. Trust the developer profile (Settings, General, VPN & Device Management).
5. Open the app and connect to your harness. The first connection to a computer on the Wi-Fi asks for local
   network access: allow it.

The limits are Apple's for free accounts, not ours: **the app stops opening after 7 days** and has to be re-signed
(AltStore and Sideloadly can refresh it while the computer is on), and an Apple ID can have **3 sideloaded apps**
active at once. That is fine for one person and hostile to a community, which is what a paid membership and
TestFlight would change (see M5).

## What CI proves

Two jobs on `macos-latest` are the whole bench, because there is no Mac in the loop. Every step is a check, and
the steps after the tests run even if the tests fail, so one push says everything that is wrong.

**`ios-app`** (about 15 minutes):

- `HarnessContractTest` (40 cases, the same file the JVM runs, against the same fixtures; 45 tests run in `:core` with the
  address parser's) and the shared module's own tests (the theme, the accent maths, the host-input parser, the connect
  failure mapping, the Connect and Pair controllers, the haptic tick rules; 116 ran at M4b, and the step wants 110) on an iOS
  simulator, over the Darwin engine and the Darwin mux socket (the fixtures are seven listeners: three harnesses, a pairing
  relay on plain HTTP and on TLS, a keep-alive WebSocket server, and one that drops a connection with no Close
  frame); a step counts the executed test cases so a skipped task cannot pass, and the next step prints the mux
  results and every delegate event the sockets saw (`MUX_…` lines), so the log says which `NSURLSession` callback
  decided each outcome;
- the Xcode project is generated, the app built for the simulator, installed and driven through the shared Connect
  screen's states: before Connect is tapped, connected, the remembered harness in the Recent list, the app coming back
  to it by itself, connected and refused in the dark scheme, refused, a harness that wants a session (401) with
  the sign-in sheet over it, a sign-in that works end to end (the token is exchanged over `NSURLSession`, the session goes to the
  Keychain and the harness that said 401 then connects) and the app coming back to that harness after a relaunch with only
  the Keychain's session to go on, a relay that wants its token (403), the refusal in French and
  in Arabic, and the form in French. Each waits for the result line the app writes, asserts it, and uploads a screenshot;
  the app's console output and any crash report are kept beside them.
- then the same for pairing (M4b), against the fixtures' pairing relays: Relay mode with nothing paired; the Pair screen;
  the camera sheet (on a simulator, the "no camera" notice); a typed pairing over plain HTTP that ends connected through
  the relay's bearer, and the app coming back to that relay after a relaunch with only the Keychain's token to go on;
  Relay mode with that relay paired; a scanned pairing; a wrong passcode (light, dark, and in Arabic, right to left); a
  lockout; an expired code; a relay that is not there; an address that is a harness and not a relay; a QR that is not a
  pairing code; and over TLS: a scanned pairing pinned to the QR's key (and the relaunch that follows, pinned from the
  stored key), a scanned pairing with a key that is not the relay's (refused, nothing stored), and a typed pairing that
  learns the key. Each asserts a `DSH_PAIR_RESULT` line, and a pairing that works also asserts the `connected` line of the
  connection it starts. The fixtures are started with the TLS relay, whose certificate and pin are made fresh each run.
- `ios-compile` also compiles `:sharedUi` for the two iOS targets and checks that the klibs exist.

**`ios-ipa`** (10 to 25 minutes depending on whether Gradle's cache has the Release link of Compose Multiplatform, which dominates it, so a separate job in parallel):
`iosApp/scripts/build-unsigned-ipa.sh` archives the Release build for a generic iOS device with signing off,
packs `DSH-Mobile-<version>-unsigned.ipa`, and fails unless it is arm64 only, unsigned, carries the repo's
version and build number, the bundle id, the 120 Hz key and the Compose resources.

*Why launch arguments and not an XCUITest.* The scenarios start the app with `-DshConnectAddress`,
`-DshAutoConnect` and the others in "The iOS app", which go down the same code path as a tap, and assert on a file the app writes: nothing
depends on typing into a Compose text field through the accessibility layer, which is the fragile part of an
XCUITest and cannot be debugged without a Mac. What a UI test would add, how Compose Multiplatform exposes text
fields and `testTag`s to XCUITest and VoiceOver, is part of what M3b has to measure, not a gate for this step.

`release.yml` does not build the `.ipa` yet; whether and when it should is a separate decision.

## The path

**M1 — shared core (done).** `core` is multiplatform and guarded by CI.

**M2 — an iOS transport.** The `RpcTransport` interface already exists; it is the seam the
OkHttp implementation sits behind. An iOS implementation has to be written against that
interface — Ktor's Darwin engine or NSURLSession directly — covering the unary POST, the
binary download and upload channels, and the `/api/remote.mux` WebSocket with its
header/auth/cookie rules (see `RpcTransport.kt` and `RelayTls.kt` for the exact carrier
contract). The shared logic above the seam moves to `commonMain` one file at a time as the
platform APIs it leans on — `java.io` streams, `java.time`, `java.util.concurrent` atomics —
are replaced with common equivalents or `expect`/`actual` pairs. Each move is verifiable:
the JVM tests that already exist keep running against the moved code.

- **M2a (done):** the seam itself and the logic directly on top of it — see "Where this
  stands".
- **M2b (done):** the Ktor-backed `RpcTransport` and `MuxSocket`, the Darwin client, the iOS failure
  classification, relay pinning, and the macOS compile gate — see "Where this stands".
- **M2c (done):** the rest of the wire layer — `DshApiClient`, `Harness021Api`, `ReasoningTranslation`,
  `RpcMultipart`, `HarnessSession`, `RelayPairing`, `HarnessLaunchLine` — and trust on first use on
  the Darwin client; see "The connect flow on iOS" for the seams and for what stayed in `jvmMain` and
  why. Also fixed: a host `end` or `error` and the mux's failure sweep could both signal one stream
  (the remove now decides, `RemoteStreamMuxConcurrencyTest` races it).

**M3 — shared UI, decided by measurement.** The UI is ~49k lines of Compose with no XML
layouts, which is the one fact that makes Compose Multiplatform plausible here. Before
committing, port one screen (Connect is the smallest real one) as a proof, run it in the
iOS simulator, and judge the feel — haptics, scrolling, text input, accessibility — against
the Android app. If CMP holds up, the app module becomes a CMP `composeApp` with thin
`androidMain`/`iosMain` walls; if it does not, the fallback is a native SwiftUI app over the
shared core, and that decision is better made on evidence than on enthusiasm.

- **M3a (done):** the first iOS app, run on CI: the `:iosShared` Compose Multiplatform module, the SwiftUI
  host and its XcodeGen project, a Connect screen that probes and handshakes over the Darwin engine, the
  simulator tests, and an unsigned `.ipa`. See "The iOS app" and "The Darwin engine on a simulator". What it
  says about Compose Multiplatform so far is only that it does not get in the way: the screen renders in the
  light and dark schemes, the 11 locales resolve from the device language (a French device shows French),
  insets are right on a Dynamic Island iPhone, and the app starts on a 120 Hz display once the plist says so.
  That is a floor, not a verdict: the feel questions below are not answered by one screen on a simulator.
- **M3b-1 (done):** the **Darwin `MuxSocket`** (`DarwinMuxSocket`), which fixed the 1 MiB message limit and the
  silent 401, and the common `platformMuxSocketFactory` the iOS Connect flow uses. See "The Darwin mux socket".
- **M3b (what is left of it):** most of the full Connect screen arrived with M4a, which shares it: the
  remembered-hosts store (`NSUserDefaults`, with the session in the Keychain, which is also where iOS's settings
  now live for the Connect screen), the launch-token sign-in, and the connection that outlives the attempt
  (`ConnectionLoop` kept running; there is no session list behind it yet). Still open: the subnet scan (Local Network
  permission and `NSBonjourServices` decisions belong here; the relay pairing flow arrived with M4b), and the part of M3 that is a
  measurement and not a build: run the full screen on a real
  iPhone, not only a simulator, and write down text input (IME, autofill, paste), scrolling and overscroll,
  haptics, VoiceOver and how Compose Multiplatform exposes `testTag`s to XCUITest, against the Android screen.
  That write-up is what decides between a Compose `composeApp` and a SwiftUI app over the shared core. What M4a
  settled is only the first half of it: Compose Multiplatform 1.7.1 draws the Android screen pixel for pixel when
  Android runs it, and draws a good iPhone screen when iOS does.
- **M4a (done):** the shared UI foundation and the Connect screen, see "The shared UI".
- **M4b (done):** the Pair screen, shared, and Relay mode on iOS, see "Pairing on iOS" and "How M4b was verified on Android". It
  was the first native-view wall (the AVFoundation scanner inside Compose) and the first time the pinned and
  trust-on-first-use Darwin clients had a screen. **The next screen is Settings** (appearance and language, which the Connect
  screen's header reaches), then the session list.

**M4 — the iOS app, one shared screen at a time (M4a above).** Xcode project, app lifecycle, and the platform walls: notifications
(UNUserNotificationCenter), background handling, QR scanning (AVFoundation), file preview,
share/save targets, the 11-language string resources (which move from Android `res/values`
to CMP string resources a screen at a time, so both apps read one set; see "Strings"). Two features are cut on iOS by the
platform, not by choice: **Termux cannot exist there** (iOS does not allow the background
processes it runs), and the always-up foreground service becomes best-effort — iOS suspends
the app, so live connection becomes notifications plus push rather than a held socket.

**M5 — building and shipping an `.ipa`.** This is the part with gates no code clears:

- **An `.ipa` requires Xcode on macOS.** It cannot be built on Windows or Linux — final
  assembly, asset processing and signing are Xcode operations. The repo has macOS
  runners for the compile gate and, since M3a, for building the `.ipa` (the `ios-ipa` job); wiring that into
  `release.yml`, the way it already produces the APK on ubuntu, is not done.
- **Signing requires Apple.** An unsigned `.ipa` installs on nothing. The options:
  the App Store / TestFlight (an Apple Developer Program membership, USD 99/year, review),
  an ad-hoc `.ipa` signed for up to 100 registered devices attached to a GitHub release
  (same membership, expires yearly), or free sideloading through AltStore/Sideloadly with a
  personal Apple ID (7-day expiry, 3-app limit — fine for one operator, hostile for a
  community). Until a membership exists, CI produces the unsigned `.ipa` as a workflow artifact (M3a) and a
  sideloading tool signs it for whoever installs it; the signed `.ipa` step lands with the account.
- **App Store review** applies only if that route is taken; connecting to a user's own
  server is well-trodden territory (Tailscale, Working Copy), but the Termux-free feature
  set and the relay's TLS profile need a pass for ATS (see "ATS and the local network" for the choice made for
  the sideloaded build and what a submission would change).

## Follow-ups

Open items the port knows about and has deliberately not done, so they are not rediscovered:

- **`WsChannel` never reports a host-initiated clean close.** It has no `onClosing` handler, so OkHttp
  never reaches `onClosed` until something fails, while `KtorMuxSocket` reports the close. M2b noted it
  and M2c left Android's behaviour exactly as it was; it is worth its own look, with a test, on the
  Android side.
- **Nothing on the Darwin side has run on a physical device.** The simulator shares the Mac's network and
  its loopback is exempt from the local-network prompt, so what a *denied* local-network permission looks
  like through `TransportFailure.ios.kt` is unknown. Also unexercised anywhere: TLS against a certificate a CA signs (the
  pinned handler and `learningChallengeHandler` ran against a self-signed fixture in M4b, see "Relay pinning on iOS"), a
  pinned socket whose stored key no longer matches, gzip, and a body that ends short of its
  `Content-Length` (the JVM's CIO check is off on Darwin). The ping answering is proven on the simulator only.
- **The QR scanner has never run on a camera.** The simulator has none, so the permission prompt, the preview, the decode
  and the Settings button of the denied state are unverified until someone scans a real pairing QR on an iPhone. Everything after
  the decode (the claim, the pin, the Keychain, the connection) is exercised through `-DshPairPayload`. Also missing next to
  Android's scanner: the flashlight, the photo picker and the sweeping laser.
- **A relay is found by pairing, not discovered.** iOS has no mDNS browse or port knock (the Local Network permission
  decisions of M3b), so Relay mode lists the relays this device has paired with and the Pair screen adds one; Android
  also offers the relays it finds on the network.
- **The device name is "iPhone".** Since iOS 16 `UIDevice.name` is that for any app without the user-assigned-device-name
  entitlement, so the relay's device list says "iPhone" unless the person edits the field. Enough to tell kinds of device
  apart, not two iPhones.
- **The iOS app builds a Darwin client per call, not one per relay.** The shared anonymous client serves the probes of
  harnesses; each pairing call and each probe of a pinned relay builds its own (pinned or learning) client and closes it,
  where the Android app keeps one `OkHttpClient` per pin. That is correct and a little wasteful (a new `NSURLSession` per probe
  of a pinned relay); caching one per pin is the change if it ever shows.
- **The permission text and display name are translated, but the app has no language setting of its own**:
  it follows the device (and iOS's per-app language setting, which `CFBundleLocalizations` enables).
- **Compose Multiplatform 1.7.1 is pinned to Kotlin 2.0.21** and moves with it. Kotlin/Native 2.0.21 builds
  and links on Xcode 26.6 (the runner today) with no changes, but a Kotlin upgrade is also where the CMP
  version, the `kotlinx-atomicfu` plugin and the Xcode compatibility have to be looked at together.
- **The `ios-ipa` job takes 10 to 25 minutes** (the Release link, cold or cached). It runs on every push; if that becomes a
  cost, restrict it to changes under `iosApp/`, `sharedUi/` and `core/`, or to main and tags.

- **iOS shows Android's wording in one failure.** `connect_fail_streams` mentions Android (see "Strings").
- **Haptics and the Keychain are verified on a simulator only.** The simulator has no Taptic Engine, and a
  Keychain item written there has not been read back across a device reboot or a device lock; the calls are made and
  the end-to-end sign-in works, which is what CI can say.
- **iOS has no Settings screen**, so there is no way to change appearance or language inside the app; it follows
  the device (and iOS's per-app language setting). The next screens in "The path" include it.
- **A harness that cannot list directories reads as unreachable.** The Recent card and "reconnect to the last harness"
  decide a named host is up by the home directory it reports, which comes from one `directoryPicker/list` call after the
  probe, so a deployment whose picker answers an error is shown "Unreachable" and is not reconnected to by itself. That is
  how the Android app has always behaved and iOS inherited it; the mock harness answers the call now so the simulator job
  can show a reachable host.
- **The Connected page on iOS is a placeholder.** It reports what the screen has to give and has nothing behind it.
- **`ios-ipa` and `ios-app` build Compose Multiplatform for iOS twice.** The shared module is bigger than the
  M3a one; if the cost of the pair matters, the Release link is the part to look at first.

## Working rules for the port

- The Android app is the product. No iOS step may regress it, and "the tests still pass on
  JVM" is the bar for every move — the conformance suite is the referee it already trusts.
- One file or one seam per change, compilable at every step; this repo does not take
  big-bang rewrites.
- Platform differences are documented where they are implemented (`expect`/`actual` pairs
  carry their reasoning in KDoc), not discovered in QA.
- A CI step that can be skipped is not a gate. Check that the thing it guards actually ran.
